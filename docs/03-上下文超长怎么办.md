# 从零手写 Agent（三）：上下文超长，别等模型替你截断

第二篇里，我做了一个比较极端的压测。

把 Ollama 的 `num_ctx` 调得很小，然后不断往 `messages` 里塞内容。

最后发现一个挺麻烦的问题：

**上下文不够的时候，Ollama 不一定报错，而是可能直接把前面的内容截掉。**

更麻烦的是，程序看起来一切正常。

`messages` 还在，接口返回 200，Agent 也给了答案。

只是模型其实已经看不到最早的那部分上下文了。

所以第三篇，我不再等模型侧处理。

这次直接把“上下文治理”放进自己的 Agent Loop：

> 每次调用 `chat()` 之前，先检查一下 messages，该截的截，该删的删。

代码核心放在：

```text
agent/context.py
```

然后用同一个压测脚本，对比：

- 什么都不做
- 主动 trim

看看两种情况下，模型到底看到了什么。

系列目录：[系列导读](./00-系列导读.md)

---

## 1. 先明确：我要解决的不是“无限 Context”

先看两种模式的区别。

| 不做处理 | 主动 trim |
|---|---|
| `messages` 在进程里一直变长 | 超过预算就删旧消息 / 截短 tool 正文 |
| 模型侧可能静默丢掉前面的内容 | 我们自己决定删什么 |
| trace 看起来历史还在 | trace 和模型实际看到的内容一致 |
| 不知道到底丢了什么 | system 里明确告诉模型有历史被省略 |

这里有一个很重要的目标：

**不是想办法让 Agent 拥有无限大的 Context。**

Context 本身就是有限的。

我要做的是：

> 在 Context 有限的情况下，让 Agent 的行为变得可预测。

至少不要出现这种情况：

```text
程序：
“我这里明明还有 12 条 messages 啊。”

模型：
“我只看到了后面几条。”
```

---

# 2. 先上两个最朴素的策略

这版没有上什么复杂的 Context Manager。

先做两个最基础的事情：

1. Tool 内容太长，先截断
2. messages 太长，删除旧消息

够用了。

## 2.1 Tool 内容太长，先截

之前 Calculator 的 tool result 只有：

```text
9
```

当然不需要处理。

但以后如果 Agent 加了一个 `fetch` 工具，情况就不一样了。

比如：

```text
role: tool

这里是一篇几万字的网页正文……
```

这种内容如果原封不动塞进 Context，很容易把窗口吃掉。

所以先对单条 `role: tool` 做限制。

默认：

```env
CONTEXT_TOOL_MAX_CHARS=2000
```

超过 2000 字符，就把后面的内容截掉，并追加：

```text
…(content truncated)
```

也就是：

```text
原始：

[一大段 tool 返回结果……]

处理后：

[前 2000 字符……]
…(content truncated)
```

这个策略比较简单，但对后面的 Agent 很有用。

尤其是联网、文件读取、搜索这类 Tool，返回内容往往比 Calculator 大很多。

---

# 3. messages 太长，再做滑动窗口

Tool 自己截断之后，还有一个问题：

**整个 messages 还是会越来越长。**

比如：

```text
system
user
assistant
tool
assistant
user
assistant
tool
assistant
...
```

聊几十轮以后，总长度还是会超过 Context。

所以第二层开始处理整个 messages。

我这里做的是一个非常简单的滑动窗口。

默认：

```env
CONTEXT_MAX_TOKENS=8000
```

先估算当前 messages 的 token 数。

如果超过预算：

1. 保留最前面的 `system`
2. 从最老的普通消息开始删
3. 一直删到估算 token 回到预算以内
4. 如果真的删过历史，就在 system 末尾加一个提示

提示类似：

```text
【注意】更早的对话已因上下文长度限制被省略…
```

这里的 token 估算也没有搞得很复杂。

直接：

```python
len(text) // 3
```

这个和前面的压测脚本保持一致。

当然，它不是 tokenizer 精确计算。

但现在的目的主要是：

> 做相对稳定的容量控制和压测对比。

不是拿它当真正的 token billing。

---

# 4. 最关键的是：trim 到底放在哪里？

这个位置其实比算法本身更重要。

Agent Loop 大概是：

```python
while ...:
    response = chat(
        messages,
        tools=tools,
    )

    ...
```

我现在把它改成：

```python
while ...:
    prepare_messages(messages)

    response = chat(
        messages,
        tools=tools,
    )

    ...
```

也就是说：

> **每一次调用 LLM 之前，都先做一次 Context 检查。**

核心代码就是：

```python
prepare_messages(messages)
```

而且是**就地修改 `state.messages`**。

不是复制一份临时 messages 给模型。

这一点后面调试的时候非常重要。

因为如果模型下一轮看到的是：

```text
A
B
C
```

那么 trace 最好也应该记录：

```text
A
B
C
```

而不是：

```text
A
B
C
D
E
F
G
```

然后实际上模型根本没看到 `D~G`。

---

# 5. 开始压测

接下来就是最有意思的部分。

我写了一个对比脚本：

```bash
python scripts/compare_context_trim.py
```

也可以分别跑：

```bash
python scripts/simulate_context_window.py \
  --num-ctx 256 \
  --chunk-chars 4000 \
  --max-rounds 6
```

开启 trim：

```bash
python scripts/simulate_context_window.py \
  --num-ctx 256 \
  --chunk-chars 4000 \
  --max-rounds 6 \
  --with-trim \
  --max-tokens 1200
```

为了让问题明显一点，我故意把：

```text
num_ctx=256
```

压得非常小。

每一轮都往上下文里灌：

```text
[块 i]
+ 一大段重复文本
```

最后统一问：

```text
最早是第几块？只答数字。
```

理论上，如果模型能看到完整历史，答案应该是最早那一块。

---

# 6. 不做 trim：messages 还在，但模型已经看不全了

先看不做 trim 的结果。

第 6 轮：

```text
--- round 6: messages=12 approx_tokens≈6703 ---
OK  reply='3'
     usage: prompt=2373 ...
```

这里最值得注意的不是答案 `3`。

而是：

```text
messages=12
approx_tokens≈6703
```

按照我们程序里的 messages 来看，历史还完整地在那里。

但是：

```text
prompt_tokens≈2373
```

一直卡在一个比较小的范围。

这说明什么？

**引擎已经开始自己截上下文了。**

于是最后模型回答：

```text
3
```

但真实最早的块并不是 `3`。

也就是说：

```text
程序认为：

[块1]
[块2]
[块3]
[块4]
[块5]
[块6]

模型实际上看到的：

        [块3]
[块4]
[块5]
[块6]
```

这就是第二篇里发现的那个问题。

最麻烦的地方在于：

**程序自己不知道。**

---

# 7. 开启 trim：我们自己决定丢什么

再跑一遍。

```text
--- round 6: messages=4 approx_tokens≈1372 ---
     trim: tokens 1372→37, dropped_msgs=1, tools_truncated=0
OK  reply='1'
     usage: prompt=93 ...
```

这次就不一样了。

trim 之后：

```text
messages=4
approx_tokens≈37
```

而：

```text
prompt_tokens=93
```

也明显降了下来。

更重要的是：

**现在 messages 里剩下的内容，就是我们主动决定留下来的内容。**

最后模型回答：

```text
1
```

这里要注意一个容易误解的地方。

它并不意味着：

> “模型终于找回了完整历史，所以正确回答了 1。”

不是。

完整的 12 轮历史本来就塞不进这个窗口。

所以两种模式其实都可能相对于“完整历史”答错。

真正的区别是：

### 不做 trim

```text
程序里的 messages 很长
        ↓
Ollama 自己截
        ↓
模型看到什么，我们不完全知道
```

### 做 trim

```text
程序里的 messages
        ↓
我们主动删掉旧内容
        ↓
剩下什么，模型就看到什么
```

所以这里追求的不是：

> “永远正确。”

而是：

> **至少让我知道模型现在到底看到了什么。**

这对调试 Agent 非常重要。

---

# 8. Calculator Agent 本身为什么不太容易触发？

回到前面一直写的 Calculator Agent。

它的上下文其实非常短：

```text
system
user
assistant(tool_call)
tool
assistant
```

所以默认：

```env
CONTEXT_MAX_TOKENS=8000
```

通常不会触发滑窗。

也就是说，平时跑：

```bash
python main.py -v "123 * 456 + 789 是多少？"
```

大概率还是正常的：

```text
system
user
assistant
tool
assistant
```

但如果开启：

```bash
python main.py -i --trace
```

然后连续聊很多轮，情况就不一样了。

这也是为什么 Context 治理不能只针对 Calculator。

现在 Calculator 很短，不代表以后所有 Agent 都很短。

一旦加入：

- 多轮对话
- 搜索
- fetch
- 文件读取
- 数据库查询
- 大段 Tool 返回结果

Context 很快就会成为问题。

---

# 9. trim 日志也要打出来

为了方便观察，我在日志里增加了类似：

```text
INFO [joyjoy] context trim: tokens 9000→7800, dropped_msgs=3, tools_truncated=0
```

这样至少能知道：

```text
原来：9000
现在：7800

删了多少：
3 条 message

Tool 有没有被截：
0
```

`--trace` 里也增加：

```text
approx_tokens≈...
```

这样就可以把自己的估算值和：

```text
usage.prompt_tokens
```

放在一起看。

这比只看：

```text
Agent 最后回答了什么
```

有用得多。

因为 Agent 出问题的时候，答案只是结果。

真正需要知道的是：

> **这一轮模型到底拿到了什么上下文？**

---

# 10. 一个目前还没解决的问题：Tool Call 配对

这里还有一个坑。

现在为了实现简单，我是：

> **按 message 一条一条删除最旧消息。**

但 Agent 的 Tool Calling 有一个天然的配对关系。

比如：

```text
assistant
tool_calls: calculator(...)

tool
9
```

这两个实际上属于同一个 turn。

如果简单地按 message 删除，极端情况下可能出现：

```text
tool
9
```

还在，

但是对应的：

```text
assistant
tool_calls: calculator(...)
```

已经被删了。

这就变成了一个“孤儿 tool”。

所以当前实现适合这个系列的最小 Agent，但如果继续往生产方向做，下一步应该改成：

> **按 turn 删除，而不是按 message 删除。**

也就是：

```text
assistant + tool
```

作为一个整体处理。

这个问题我先留在这里，后面继续扩展 Agent Loop 的时候再处理。

---

# 11. 那 Ollama 的 `num_ctx` 和我们的 trim 到底谁说了算？

其实是两层。

第一层是我们自己的：

```python
prepare_messages(messages)
```

它决定：

> **到底把哪些 messages 发给 API。**

第二层是 Ollama：

```text
num_ctx
```

它决定：

> **模型最终能处理多大的上下文。**

所以即使我们自己做了 trim，也不能认为：

```text
prepare_messages()
```

之后就绝对安全。

如果我们自己控制在：

```text
8000
```

但 Ollama：

```text
num_ctx=2048
```

那模型侧还是可能继续截。

所以完整链路其实是：

```text
原始 messages
      ↓
Tool 内容截断
      ↓
滑动窗口
      ↓
prepare_messages()
      ↓
发送给 Ollama
      ↓
num_ctx 再做最终容量限制
      ↓
模型
```

这也是为什么压测的时候，我会故意把：

```text
num_ctx
```

调得很小。

这样可以更容易把问题暴露出来。

---

## 12. 可选关闭 trim 与前三篇串起来

**注意：** `CONTEXT_TRIM_ENABLED=false` 会回到第二篇行为 — messages 堆长、Ollama 可能静默截断。trim 不是神秘组件，只是 **Loop 里的 Context Governance**，与具体 Tool 无关。

前三篇串线：Tool+Loop → `messages` 短期记忆 → **`prepare_messages`（tool 截断 + 滑窗）** → 再进 LLM。压测要对比 **无 trim / 有 trim** 的 `prompt_tokens` 与模型是否还能看到开头，而不是只写一句「需要滑窗」。

---

## 13. 收束

**注意：**

- Context 不够时 **别等报错** — 可能静默截断。
- 最小组合：**Tool 返回截断** + **滑窗删旧消息**；在每次 `chat()` 前 `prepare_messages(state.messages)`，让 trace 与模型所见一致。
- 压测同时看：`messages` 条数、估算 token、`prompt_tokens`、trim 日志、最终答案。
- 按条删 message 可能拆散 `tool_calls` 与 `tool` 配对 — 后续可改按 turn 删、摘要压缩、更准 token 计数。
- 联网 `fetch` 后，**Tool 内截断 + Loop trim** 两层会一起起作用（第四篇起更明显）。
