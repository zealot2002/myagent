# 从零手写 Agent（三）：上下文超长——截断、滑窗与压测对比

第二篇用压测脚本看到：**Ollama 在窗口不够时，Often 不报错，而是静默截断**。  
第三篇在 **主 Agent Loop 里接上治理**：在每次 `chat()` 前 **主动 trim**，并和「什么都不做」做对比。

代码在文末仓库；核心模块 **`agent/context.py`**。

---

## 1. 要解决什么问题？

| 不做处理 | 主动 trim |
|----------|-----------|
| `messages` 在进程里一直变长 | 超过预算就 **删旧消息 / 截短 tool 正文** |
| 模型侧可能 **静默丢头** | 我们控制 **删什么**，并在 system 里 **声明已省略** |
| trace 看起来「历史还在」，模型却看不见 | trim 后 trace **与模型所见一致**（就地修改） |

目标不是「无限 context」，而是 **在有限窗口内可预期地退化**。

---

## 2. 策略：两层，都很朴素

### 2.1 截断 Tool 的 `content`

单条 `role: tool` 的正文若超过 **`CONTEXT_TOOL_MAX_CHARS`**（默认 2000 字符），尾部改为：

```text
…(content truncated)
```

适合将来 **大段 fetch 结果**；对 calculator 的 `"9"` 无影响。

### 2.2 滑动窗口（删旧 message）

估 token 总和超过 **`CONTEXT_MAX_TOKENS`**（默认 8000）时：

- **保留** `[0]` system（若有）
- **从 `[1]` 起删最旧的一条**，直到估 token ≤ 预算或只剩 system + 一条
- 若删过历史，在 system 末尾追加 **【注意】更早的对话已因上下文长度限制被省略…**

估 token 用 **`len(text)//3`**，与压测脚本一致；不是 tiktoken 精度，但 **够做相对对比**。

### 2.3 接入点

`agent/loop.py` 里，**每次** `chat(messages, tools=…)` **之前**：

```python
prepare_messages(messages)  # 就地修改 state.messages
```

配置见 `.env.example`：`CONTEXT_TRIM_ENABLED`、`CONTEXT_MAX_TOKENS`、`CONTEXT_TOOL_MAX_CHARS`。

---

## 3. 压测对比：同一脚本，开/关 trim

最后一轮统一问：**「最早是第几块？只答数字。」**  
前面每轮灌 `[块 i]` + 大段重复文本；`num_ctx=256` 故意压小。

```bash
python scripts/compare_context_trim.py
# 或
python scripts/simulate_context_window.py --num-ctx 256 --chunk-chars 4000 --max-rounds 6
python scripts/simulate_context_window.py --num-ctx 256 --chunk-chars 4000 --max-rounds 6 --with-trim --max-tokens 1200
```

**A. 无 trim（节选，第 6 轮）：**

```text
--- round 6: messages=12 approx_tokens≈6703 ---
OK  reply='3'
     usage: prompt=2373 ...
```

messages 条数 **12**，自估 token **6703**，但 `prompt_tokens` 仍卡在 ~2370——**引擎已截断**；模型答 **3**，与真实最早块 **对不齐**。

**B. 有 trim（节选，第 6 轮）：**

```text
--- round 6: messages=4 approx_tokens≈1372 ---
     trim: tokens 1372→37, dropped_msgs=1, tools_truncated=0
OK  reply='1'
     usage: prompt=93 ...
```

trim 后 **只剩 3 条 message、估 37 token**；`prompt_tokens=93`。答 **1** 反映的是 **仍留在窗口里的最早块**，而不是完整 12 轮历史。

**注意：**

- 两种模式 **都可能答「错」相对「全部历史」**——窗口本来装不下全部块；差别是 **trim 让「模型可见」与「列表长度」一致**，并留下 **日志 / system 提示**。
- 无 trim 时 **列表很长但模型看不见开头**；更隐蔽。

---

## 4. 和主 Agent（Calculator）的关系

Calculator 对话短，默认 **8000 估 token** 往往 **不会触发滑窗**；治理逻辑 **先挂上**，`-v` 里若 trim 会出现：

```text
INFO [joyjoy] context trim: tokens 9000→7800, dropped_msgs=3, tools_truncated=0
```

`--trace` 末尾增加 **`approx_tokens≈…`**，便于和 `usage.prompt_tokens` 对照。

交互模式 `-i` 聊很多轮后，**更可能触发**滑窗——这正是 **多轮 + 窗口** 要在产品里一起设计的原因。

---

## 5. 常见困惑

**Q：trim 改的是副本还是 state？**  
**就地改 `state.messages`**。这样 trace 就是模型下一步还能不能用的上下文。

**Q：删消息会不会破坏 tool_calls 配对？**  
当前实现 **按条删最旧**，极端情况下可能留下「孤儿 tool」。生产环境更稳妥的是 **按 turn 删**（assistant+tool 成对）；后续可加强。

**Q：和 Ollama 的 `num_ctx` 谁说了算？**  
两层：**我们**的 `prepare_messages` 控制 **发给 API 的 messages**；**Ollama** 的 `num_ctx` 仍可能再截一层。本地压测可同时调小 `num_ctx` 做极端实验。

**Q：关 trim？**  
`.env` 里 `CONTEXT_TRIM_ENABLED=false`，行为回到第二篇的「只堆不裁」（仍可能遭引擎静默截断）。

---

## 6. 小节

1. **静默截断** 要靠 **主动治理**，不能等 API 报错。
2. **截 tool 正文 + 滑窗删旧消息** 是最小可行组合；system **声明省略**。
3. **`prepare_messages` 在 Loop 里、每次 LLM 前** 调用，与 Tool 无关，所有 Agent 共用。
4. **`compare_context_trim.py`** 用同一问题对比 **列表长度 / prompt_tokens / 答案**。
5. 更精细的 **按 turn 删除、摘要压缩** 可以在此基础上再加。
