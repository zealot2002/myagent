# 从零手写 Agent（二）：短期记忆，其实就是你一直带着的 messages

上一篇把 Tool 跑通以后，我开始给 Agent 加多轮对话。

然后很快就踩了一个特别容易踩的坑。

我先运行：

```bash
python main.py --trace "3*3"
```

程序正常算出了 9。

接着，我又开了一个命令：

```bash
python main.py --trace "刚才我问了什么问题？"
```

结果模型当然答不上来。

当时第一反应是：

> Agent 怎么连上一句话都记不住？

后来顺着 `messages` 和 trace 一路看下去，我才发现，这个问题其实一点都不神秘。

**所谓短期记忆，本质上就是：下一次请求的时候，你有没有把之前的 `messages` 一起带给模型。**

没有什么隐藏的 Memory 模块。

也没有模型偷偷替你保存上一轮聊天记录。

你把历史放进上下文，它就能看到；你没放，它就真的不知道。

这件事听起来简单，但它直接牵扯到 Agent 里一个非常核心的问题：

> **上下文窗口到底是什么？为什么 Agent 聊得越久越容易出问题？**

这篇就从我踩的这个坑开始，把这几个问题捋清楚。

---

## 1. 我之前理解的“记忆”，其实有点想多了

先看最简单的 Chat Completions 流程。

每次调用 LLM，大概都是：

```text
messages
   ↓
LLM
   ↓
assistant / tool_calls
   ↓
append 到 messages
   ↓
下一次继续发送整个 messages
```

代码层面其实就是：

```python
response = llm(messages, tools=tools)

messages.append(response)
```

下一轮：

```python
response = llm(messages, tools=tools)
```

还是把当前的 `messages` 整体传进去。

所以我现在比较愿意用一句话来理解：

> **短期记忆 = 当前还留在 `messages` 里的历史。**

比如一次 Calculator Agent：

```text
[0] system
[1] user: 3*3
[2] assistant: tool_calls → calculator
[3] tool: 9
[4] assistant: 3*3 的结果是 9
```

下一轮用户再问：

```text
刚才我问了什么问题？
```

只要新的 user message 继续 append 到这个列表里：

```text
[0] system
[1] user: 3*3
[2] assistant: tool_calls
[3] tool: 9
[4] assistant: 3*3 的结果是 9
[5] user: 刚才我问了什么问题？
```

模型就能看到之前发生过什么。

所以 Agent 里的 `State`，在我这个最小实现里，核心其实就是这个：

```python
messages
```

我额外写的 `AgentState`，更多只是给这个列表套一层壳，再放一些调试信息，比如：

```text
steps
tool_results
```

真正给模型看的，还是 `messages`。

---

## 2. 那为什么我刚才换一个命令，模型就“失忆”了？

现在回头看就很容易解释了。

我之前运行的是：

```bash
python main.py --trace "3*3"
```

这个进程结束以后，里面的 `AgentState` 也没了。

然后我又运行：

```bash
python main.py --trace "刚才我问了什么问题？"
```

这已经是一个**全新的进程**。

它拿到的 messages 只有：

```text
system
user: 刚才我问了什么问题？
```

根本没有：

```text
user: 3*3
```

模型当然不知道。

所以这里有个特别重要的区别：

### 同一个进程

```bash
python main.py -i
```

然后：

```text
你> 3*3
你> 刚才我问了什么问题？
```

第二句话可以看到第一句话。

因为两次输入都 append 到了同一个 `messages`。

### 两个独立进程

```bash
python main.py --trace "3*3"

python main.py --trace "刚才我问了什么问题？"
```

第二个进程没有第一条消息。

自然也就不存在所谓的“刚才”。

所以：

> **多轮对话不是模型自己记住了，而是程序一直把历史带着。**

这一点我觉得是理解 Agent Memory 最重要的第一步。

---

## 3. 那上下文窗口又是什么？

搞明白 `messages` 之后，下一个问题马上就来了：

> 如果一直 append，不就可以一直记了吗？

当然不行。

因为模型一次能处理的 token 是有限的。

这个限制，就是：

> **上下文窗口（Context Window）**

我现在比较喜欢把它理解成：

**模型一次请求最多能装多少 token 的工作区。**

而 `messages` 就是往这个工作区里不断塞东西。

比如：

```text
system
user
assistant
tool
assistant
user
assistant
tool
...
```

这些内容都要占上下文。

而且别忘了，Tool 也会占。

比如一个简单 Calculator Agent：

```text
system
user
assistant + tool_calls
tool
assistant
```

看起来没多少内容。

但如果以后把 Tool 换成：

```text
fetch_web_page()
```

返回一整页网页：

```text
tool
└── 几万字网页正文
```

那情况就完全不一样了。

**消息条数可能没增加多少，但 token 一下就上去了。**

所以 Agent 比普通 Chat 更容易碰到上下文问题。

---

## 4. 上下文窗口和 MAX_STEPS，不是一回事

这里我也踩过一个容易混淆的概念。

我的 Agent 里有：

```python
MAX_STEPS
```

比如：

```python
MAX_STEPS = 10
```

它表示：

> 一次任务最多调用多少次 LLM。

而上下文窗口表示：

> 每一次调用 LLM，最多能塞多少 token。

两个完全不是一个维度。

比如：

```text
MAX_STEPS = 2
```

也可能出问题。

因为第一轮 Tool 返回了 10 万字。

虽然只跑了两步，但第二次请求已经可能装不下。

反过来也一样。

你可以：

```text
MAX_STEPS = 20
```

但每一步都很短，整个上下文也可能还没到上限。

所以可以简单记成：

```text
MAX_STEPS
    ↓
最多跑多少步

Context Window
    ↓
每一步最多能装多少 token
```

这两个东西后面都会影响 Agent，但解决的是不同的问题。

---

## 5. 我打开 trace 以后，终于看清楚“记忆”到底是什么

比如执行：

```bash
python main.py --trace "3*3"
```

典型的 messages：

| 下标 | role | 内容 | 占上下文吗 |
|---|---|---|---|
| `[0]` | system | 系统规则、时间 | 是 |
| `[1]` | user | `3*3` | 是 |
| `[2]` | assistant | tool_calls | 是 |
| `[3]` | tool | `9` | 是 |
| `[4]` | assistant | 最终答案 | 是 |

这一张表其实就把很多问题说明白了。

比如第一篇讲的 Tool。

Tool 调完以后，结果并不是：

> “计算完成，然后从 Agent 里消失。”

而是：

```text
[3] tool: 9
```

这条消息还留在 `messages` 里。

所以第二次调用 LLM 时：

```text
[0]
[1]
[2]
[3]
```

这些历史仍然会一起送进去。

模型看到：

```text
user: 3*3
assistant: tool_calls
tool: 9
```

它自然就知道刚才发生了什么。

---

## 6. 一个容易误解的地方：tool_results 是不是记忆？

我的 `AgentState` 里还有一个：

```python
tool_results
```

里面也会保存：

```text
calculator → 9
```

刚开始我也会觉得：

> 那模型是不是同时从 `tool_results` 里读取结果？

不是。

`tool_results` 只是我自己为了调试和记录留的一份副本。

模型真正看到的是：

```text
role: tool
```

对应的 message。

所以：

```text
AgentState.tool_results
```

和：

```text
messages[].role == "tool"
```

不是一回事。

前者主要是给程序和人看的。

后者才是模型上下文的一部分。

---

## 7. Agent 为什么比普通 Chat 更吃上下文？

这个问题到这里就比较好理解了。

普通 Chat 可能就是：

```text
user
assistant
```

而 Agent 一次问题可能变成：

```text
system
user
assistant + tool_calls
tool
assistant
```

如果一次任务里连续调用多个 Tool：

```text
system
user
assistant + tool_calls
tool
assistant + tool_calls
tool
assistant
```

消息越来越长。

更麻烦的是，Tool 返回的内容有时候也非常长。

比如：

```text
search_web
```

返回一大段网页。

或者：

```text
read_file
```

把几万字日志直接塞进：

```text
role: tool
```

那上下文很快就会被吃掉。

所以我现在看 Agent 的上下文问题，会特别注意三个东西：

| 现象 | 背后的原因 |
|---|---|
| 对话越来越慢、越来越贵 | 每次请求都要重新带历史 |
| Tool 返回特别长 | Observation 占掉大量上下文 |
| Agent 跑很多步 | 每一步都会留下新的 message |

也就是说：

> **Agent 的每一步，不只是增加一次调用，也是在给下一次请求增加上下文负担。**

---

## 8. “每轮都把 messages 全发一遍”，是不是很浪费？

是。

但这是当前这种实现方式本身决定的。

比如：

```text
第一次：
system + user

第二次：
system + user + assistant + tool

第三次：
system + user + assistant + tool + assistant + user
```

每次请求都会带上当前完整历史。

所以第二次并不是只告诉模型：

```text
刚才 Tool 返回了 9。
```

而是把整个上下文重新带过去。

这也是为什么多轮 Agent 的 token 成本会不断增加。

当然，具体怎么计费要看平台。

但从实现角度看，有一点是确定的：

> **你让模型每一轮重新看到完整历史，就意味着每一轮都要重新处理这些历史。**

这不是 Loop 写错了。

而是这种上下文工作方式本身就是如此。

---

## 9. 那上下文到底能有多长？

这个问题很容易被各种模型宣传页搞得特别复杂。

因为不同模型、不同版本、不同 endpoint，窗口都可能不一样。

所以我这里不想把某个数字当成永久真理。

查模型规格时，最好还是以：

```text
官方文档
+
你实际使用的 endpoint
```

为准。

我当时本地跑的是：

```text
qwen2.5:3b
```

通过：

```bash
ollama show qwen2.5:3b
```

看到本机配置的 context length 是：

```text
32768
```

而且还有一个容易忽略的问题：

> **模型本身支持多大的 context，和你实际运行时给它多大的 context，不一定是一回事。**

Ollama 运行时还会受到：

```text
num_ctx
```

等配置影响。

所以不要看到模型卡上写了一个数字，就默认自己的 Agent 一定能用满。

## 10. 我专门做了一次压力测试

理论说到这里还不够。

于是我专门写了一个脚本，故意把上下文窗口调得特别小：

```bash
python scripts/simulate_context_window.py \
    --num-ctx 256 \
    --chunk-chars 8000 \
    --max-rounds 5
```

目的很简单：

每一轮往 messages 里塞一大块文本，然后继续调用 LLM。

看看上下文爆掉以后，到底会发生什么。

正常情况下，我们可能会以为：

```text
context 超了
↓
API 报错
↓
程序知道出问题了
```

但本地 Ollama 的实际表现有点不一样。

我当时看到的日志类似：

```text
--- round 1: messages=2 approx_input_tokens≈2677 (limit num_ctx=256) ---
OK  usage: prompt=2050 completion=301 total=2351

--- round 5: messages=10 approx_input_tokens≈14192 (limit num_ctx=256) ---
OK  usage: prompt=2050 completion=486 total=2536
```

最让我注意的是：

```text
messages
```

明明越来越长。

但：

```text
prompt_tokens
```

却差不多卡在一个范围。

也就是说：

**程序里的历史还在增长，但真正进入模型的上下文已经被截断了。**

---

## 11. 这比直接报错还麻烦

如果 API 直接告诉你：

```text
context length exceeded
```

其实很好办。

你看到错误就知道：

> 上下文满了。

但静默截断就麻烦了。

因为程序可能还是：

```text
HTTP 200
```

甚至正常返回一个答案。

只是模型已经看不到最早那些内容了。

于是就可能出现这种情况：

```text
程序里的 messages：

[1] 很早之前的重要信息
[2]
[3]
[4]
...
[10] 最近的信息
```

你打开 trace 一看：

> 历史不是都在吗？

但模型真正看到的可能只有：

```text
[7]
[8]
[9]
[10]
```

于是最早的信息就像“失忆”了一样。

更麻烦的是，模型通常不会告诉你：

> “抱歉，前面的上下文被截掉了。”

它可能直接根据自己现在看到的内容继续回答。

这就是我觉得上下文超长特别麻烦的地方：

**程序层面看起来还正常，模型层面其实已经不是你以为的那个上下文了。**

---

## 12. 所以，短期记忆其实是有保质期的

到这里，我对“短期记忆”这个词的理解也发生了一点变化。

它并不是：

```text
模型记住了所有聊天内容
```

而更接近：

```text
当前 messages
    ↓
能放进 context window
    ↓
模型才能看到
```

所以真正的链路是：

```text
历史消息
   ↓
messages
   ↓
上下文窗口
   ↓
模型
```

任何一层出了问题，所谓“记忆”都会出问题。

比如：

### 历史根本没保存

```text
换了一个进程
```

模型当然不知道。

### 历史保存了，但太长

```text
context window 不够
```

模型可能看不到前面的内容。

### Tool 返回太长

```text
Observation 吃掉大量窗口
```

早期对话就更容易被挤出去。

所以：

> **“模型记不记得”很多时候不是模型有没有 Memory，而是你到底给了它多少上下文。**

---

## 13. 长期记忆、治理方向、Tool 占窗口（合并说清）

**注意：**

- **短期记忆** = 仍在 `messages` 里、每轮请求都会带上 → 受 Context Window 限制。
- **长期记忆** = 文件 / DB / 向量库；用时检索再 **插入 messages**。RAG 不是绕过窗口，而是 **先筛再塞**。
- **messages 不能无限 append** — 满了就要治理。常见手段：滑窗、摘要、Tool 结果截断、按需检索；第三篇先落地 **截断 + 滑窗**。
- **`assistant(tool_calls)` 与 `tool` 结果都会留在上下文** — Calculator 返回 `9` 几乎无感，整页 `fetch_url` 则会迅速吃满窗口（第四篇更明显）。

---

## 14. 收束

**注意：**

- **短期记忆 ≈ `messages`**；「记得上一句」是因为下次请求仍带上它们。
- **多轮** 要同进程 State（如 `python main.py -i`）；两次独立命令是两次冷启动。
- **Context Window** 是模型一次能看的 token 上限，不是 `messages` 列表长度。
- **Agent 更吃 token**：`tool_calls` + 长 tool 正文会快速占满窗口。
- **Ollama 可能静默截断** — `messages` 还在变长，进模型的 prompt 已丢开头；用 `--trace` 和 `prompt_tokens` 对照，不要只看最终答案。
