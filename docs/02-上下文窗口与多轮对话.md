# 从零手写 Agent（二）：短期记忆就是上下文窗口

第一篇把 Tool 讲清楚之后，我接着写 `AgentState`、加 `-i` 多轮，然后踩了一个很蠢的坑：  
先 `python main.py --trace "3*3"`，再 **另开一条命令** 问「刚才我问了什么问题？」——模型当然答不上来。

那一刻我才把话说完整：**所谓短期记忆，不是神秘模块，就是每一轮请求里带过去的 `messages`，整体塞进模型的上下文窗口（context window）。**  
没有单独「记忆 API」；**记不记得住，取决于这段 prompt 里有没有、还能不能装下。**

这篇围绕 **上下文长度、多轮对话、我遇到的困惑** 展开。Loop 仍会出现，但不再是主题。代码在文末仓库。

---

## 1. 我原来的理解对不对？

**大体对。**

在 Chat Completions 这条路上：

```text
每次 llm(messages, tools=...)
    → 把当前 messages 列表（+ tools 定义等）编码成 token
    → 模型在这些 token 上做续写
    → 返回新的 assistant（或 tool_calls）
    → 你 append 回 messages
    → 下一轮再整包发送
```

所以：

- **短期记忆 = 会话内已经 append 进 `messages` 的一切**（system、user、assistant、tool）。
- **不是**模型在服务端帮你「记着上次进程」——**上次 shell 命令结束，state 就没了**。
- **每一轮 Loop**（同一次用户问题里 step 1、step 2）也是 **整段 messages 重发**，不是只发「新增那一行」。

Agent 公式里的 **State**，在最小实现里 **主体就是 messages**；`AgentState` 只是给这个 list 套了壳，方便多轮 `-i` 和调试字段（`steps`、`tool_results`）。

---

## 2. 上下文窗口是什么？和 prompt 什么关系？

我用的说法：

> **上下文窗口** = 模型 **单次 forward 能处理的 token 上限**（输入 + 输出共享预算，具体看厂商怎么扣）。

`messages` 拼起来就是 **输入 prompt 的主体**（还要加上 tools 的 schema 等，也占 token）。  
窗口满了之后，不能指望「无限往上 append」——必须 **截断、摘要、换存储**，否则 API 报错或悄悄丢头/丢尾。

我现在的 Ollama 小模型，窗口比 GPT-4 类小很多；**Agent 比纯 Chat 更费 token**，因为同一问题里就有：

```text
system
user
assistant + tool_calls
tool（Observation，有时很长）
assistant
… 下一轮 user …
```

**困惑：** 「窗口长度」和 **`MAX_STEPS`** 是一回事吗？  
**不是。** `MAX_STEPS` 是我代码里的 **最多调几次 LLM**；上下文窗口是 **每次调用能塞多少 token**。  
可以 2 步就答完，但 messages 已经很长；也可以步数少，但每条 tool 返回半本书。

---

## 3. 多轮对话：什么时候「记得住刚才」？

### 3.1 同进程、同一份 `messages` → 记得住

```bash
python main.py -i --trace
你> 3*3
你> 刚才我问了什么问题？
```

第二条 user 会 **append** 在第一次的 assistant 后面。  
下一次 `chat(messages, …)` 时，模型 **能在上下文里看到** `[1] user: 3*3` 和后面的 tool/assistant——这就是 **多轮短期记忆**。

### 3.2 两条 shell 命令 → 记不住（我踩的坑）

```bash
python main.py --trace "3*3"
python main.py --trace "刚才我问了什么问题？"
```

第二次是 **新进程、新 `AgentState`**，messages 只有：

```text
system + user: 刚才我问了什么问题？
```

没有任何「3*3」。模型说「请提供上一次查询的信息」是 **诚实** 的——**不是 Loop 坏了，是根本没有历史进窗口**。

**注意：** 多轮对话 = **刻意让多次 user 输入进同一条 messages**；换命令行 = 新会话，除非你自己做持久化（写文件、数据库），那是 **长期记忆** 范畴。

---

## 4. 读 trace：窗口里到底装了什么

`python main.py --trace "3*3"` 典型结果：

| 下标 | 角色 | 占窗口吗 |
|------|------|----------|
| `[0]` system | 规则 + 注入时间 | 是 |
| `[1]` user | 3*3 | 是 |
| `[2]` assistant | tool_calls | 是 |
| `[3]` tool | 9 | 是 |
| `[4]` assistant | 最终人话 | 是 |

**同一次提问、两步 Loop：** 第 2 次 call LLM 时，**[0]–[3] 全部还在**，再加新的 assistant。  
所以 Tool 的 Observation **不会**「调完就丢」——只要还在 `messages` 里，就在 **下一轮 prompt** 里。

**困惑：** `tool_results` 列表算不算记忆？  
我代码里那是 **给人类调试用的副本**；模型 **不看** 这个字段，只看 `role: tool` 的 message。

**困惑：** `steps=2` 是什么？  
累计 **调了几次 LLM**（交互多题会继续涨），**不是** token 数。

---

## 5. Agent 为什么比聊天更吃上下文？

纯 Chat：一轮 user + 一轮 assistant。  
Calculator Agent 一问：

```text
system + user + assistant(tool_calls) + tool + assistant
```

五步消息才结束，**token 至少是纯 Chat 的几倍**。  
一旦 Tool 会拉回 **大段外部文本**（整页网页、长日志、JSON  dump），**Observation 的 content** 会暴涨——这和 **窗口长度** 会直接冲突。

我现在的直觉：

| 现象 | 和窗口的关系 |
|------|----------------|
| 对话越长，越慢、越贵 | 每次整包编码 |
| tool 返回太长 | 占满窗口 → 挤掉早期 system/user |
| 多 Tool 多步 | 消息条数多，结构重复（每条 tool 一行） |

**截断 / 摘要** 若不做，长对话或长 Tool 结果很容易顶满窗口——有时问题先出在 context，而不是 Loop 写错。

---

## 6. 常见模型的上下文窗口（参考表）

窗口长度 **会变**（厂商改版、API 档位、是否扩展上下文模式）。查规格时以 **当前官方文档** 和 **你实际用的 endpoint** 为准。  
本地 Ollama 另有一条：模型卡片上的 `context length` 是 **能力上限**；运行时还可被 **`num_ctx`**、显存/内存 **截小**。

| 模型 / 系列 | 上下文（约，单位 token） | 备注 |
|-------------|---------------------------|------|
| **GPT-4o** | 128k | OpenAI 通用对话档 |
| **GPT-4.1 / 4o mini** | 128k 级 | 以 OpenAI 当期说明为准 |
| **o1 / o3 等推理档** | often 低于同价对话模型 | 输入+思维链+输出共用预算 |
| **Claude 3.5 Sonnet** | 200k | Anthropic |
| **Claude 3 Opus / 4 系** | 200k 级 | 长文场景常见 |
| **Gemini 1.5 Pro** | 1M（宣传档） | 实际产品可能有软限制 |
| **Gemini 2.0 Flash** | 1M 级 | Google 文档需单独核对 |
| **Llama 3.1 8B/70B** | 128k | Meta 权重说明 |
| **Qwen2.5-7B/72B** | 128k 级 | 阿里系常见标称 |
| **我们用的 Ollama `qwen2.5:3b`** | **32768** | 本机 `ollama show qwen2.5:3b` → `context length 32768`；支持 **tools** |

**和 Agent 的关系：** tools 的 JSON schema、每一步 `role: tool` 的正文，都占同一窗口。Calculator 一问只占几条 message；换成「拉回整页 HTML」的 Tool，**条数不变，token 暴涨**。

## 7. 模拟测试：不做处理时会发生什么？

仓库脚本（不改动主 Agent，单独压测）：

```bash
python scripts/simulate_context_window.py --num-ctx 256 --chunk-chars 8000 --max-rounds 5
```

**思路：**

1. 故意把 Ollama 的 **`num_ctx` 设很小**（例如 256），否则 32k 要灌很久。
2. 每轮往 `messages` 里 **append 一大块重复 user 文本**，再 call 一次 LLM（整包 history）。
3. 看 API **报错还是静默**、返回里的 **`usage.prompt_tokens`** 是否触顶、模型答的是否还「记得」最早说了啥。

**本机实测摘录（`qwen2.5:3b`，`num_ctx=256`，每块约 8000 字符）：**

```text
--- round 1: messages=2 approx_input_tokens≈2677 (limit num_ctx=256) ---
OK  usage: prompt=2050 completion=301 total=2351

--- round 5: messages=10 approx_input_tokens≈14192 (limit num_ctx=256) ---
OK  usage: prompt=2050 completion=486 total=2536
```

**注意（Ollama + 当前脚本）：**

| 现象 | 含义 |
|------|------|
| **没有抛 HTTP 4xx** | 不像部分云端 API 直接 `context length exceeded`；请求仍 **200 OK** |
| **`prompt_tokens` 卡在 ~2050 附近** | 实际进模型的 prompt **被截断到预算内**（与 `num_ctx=256` 不完全字面相等，还受实现与生成预留影响） |
| **脚本里 `approx_input_tokens` 一直涨** | `messages` 列表在进程里 **仍然变长**——Agent 若不做裁剪，**内存与日志**也会涨 |
| **回复开始「讲窗口压力测试」** | 模型 **看不到** 最早几轮 user 块的内容，只能基于 **截断后可见的尾巴** 胡编，**不会**告诉你「前面被截掉了」 |

也就是说：**「不做处理」在 Ollama 上 Often 不是程序 crash，而是 silent truncation + 答非所问 / 遗忘早期 Tool 结果**——比报错更阴间，要靠 **`usage`、trace、或自估 token** 才发现。

云端（OpenAI 等）在超长时 **更常直接拒绝**；本地引擎 **更常截断继续跑**。Agent 要统一处理的话，不能假设「一定会报错」。

第三篇已在主 Loop 接入 **`agent/context.py`**（截 tool + 滑窗）；本篇压测仍可用于对比「引擎静默截断」。

## 8. 常见困惑（自问自答）

**Q：每轮都整包发 messages，会不会重复计费/重复「思考」？**  
会。每次 API call 都对 **当前完整输入** 算 token（具体 pricing 看平台）。Agent 的 step 2 不是「只读 tool 结果那一行」，而是 **整段历史再读一遍**。这是设计如此，不是实现 bug。

**Q：system 注入的时间，占不占窗口？**  
占。在 `[0]`，每轮请求都在。交互模式里我用 `refresh_system_prompt()` 更新 `[0]`，字变一点，token 变一点。

**Q：「长期记忆」和短期怎么分？**  
我现在的划分：**还在 `messages` 里、随请求带进模型的 = 短期（窗口内）**；**写磁盘/向量库、按需检索再塞进 messages = 长期**。RAG 是「先检索，再 insert 进 prompt」，仍然受窗口限制。

**Q：窗口满了怎么办？**  
见 **§7 模拟**；工程上常见：滑动窗口、摘要、截断 Tool 正文、检索后只注入片段。框架 **checkpoint** 是持久化 state，**不**等于无限 context。

**Q：和 LangGraph 的 State 是一回事吗？**  
Graph 里的 `messages` 字段，本质仍是 **要喂给 LLM 的那份列表**；图只是帮你 **谁在什么时候改 state**。窗口约束 **不变**。

## 9. 和第一篇的衔接

- **Tool** 会在 messages 里留下 **assistant(tool_calls) + tool** 两行，**永久占坑直到被截断**。
- **调优**（日期、拒答）改的是 **system 占窗口里哪一段字**，不是换记忆机制。
- **Loop** 保证多步；**窗口** 保证多步 **还能不能全部塞进模型**——两个维度。

---

## 10. 小节

1. **短期记忆 = `messages` = 每次请求带进模型的上下文**；没有隐藏记忆区。
2. **多轮** 要在 **同一进程、同一 state** 里 append user；换命令 = 新会话。
3. **上下文窗口** 是 token 预算；**`MAX_STEPS`** 是调用次数上限；Agent **更费 token**。
4. Tool 结果、大段外部文本、长对话都会 **挤窗口**；截断、摘要、检索再写入 prompt 是常见应对。
5. **`--trace`** 是看「窗口里到底有什么」的最好习惯。
6. **§6 表 + §7 脚本** 用来查上限、复现「静默截断」；处理策略另写（尚未接入 `main.py`）。
